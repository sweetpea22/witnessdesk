# How the recipient graph gets its information

The demonstration starts with six locally stored fictional article excerpts in `fixtures/recipient-portfolios.ts`. These are synthetic public-portfolio inputs, not scraped evidence or real journalists. A local Ollama model reads only that corpus and extracts specialties with exact supporting quotations. The API can alternatively use configured Darkbloom credentials over the same fixed corpus. The app never sends the incoming whistleblower tip or private match query to Darkbloom.

Each output must use an existing recipient ID, the supplied region, allowed specialties, and exact quotations from that person's own sources. Both articles must support the profile. Unsupported outputs reject the run. Before any successful model run, the app uses explicitly marked curated fixture profiles. A failed run retains the previous valid profiles and their original preparation labels.

Ollama uses [structured outputs](https://docs.ollama.com/capabilities/structured-outputs). For this small demonstration, the JSON schema constrains its choices to literal sentences in each article that contain an allowed specialty. Those candidates come from the source text, independently of the curated fallback. The model chooses the supported profile edges; the validator checks its answer again. One correction turn is allowed, with no relaxation of the provenance checks.

The graph is built deterministically from validated extraction: recipient → authored article → supported specialty, plus recipient → reporting region. Every relationship carries a source document ID. This is an expertise graph, not an identity or trust verification system.

Private matching uses the selected analysis provider on the desk: Ollama locally, or the verified Tinfoil SDK when explicitly configured. It receives the validated profiles and may return only known recipient IDs. A deterministic topic-term matcher is also included and unit-tested as a baseline; the live demo uses the model's selection. No tip or matching query goes to Darkbloom, and no match is an identity or trust score.

Successful synthetic preparation can be cached in `fixtures/prepared-demo.json` with the corpus hash, provider, model, run ID and timestamps. It contains only the fictional public corpus's extracted facts. It is loaded only if the source corpus hash and validations still match. A cached run is preprocessing, not a live request on every page load.

Set `DARKBLOOM_API_KEY`. The verified demo defaults are `DARKBLOOM_BASE_URL=https://api.darkbloom.dev/v1` and `DARKBLOOM_MODEL=gemma-4-26b`; both can be overridden. The [official API console](https://console.darkbloom.dev/api-console), checked 2026-11-07, documents base `https://api.darkbloom.dev/v1`, `POST /v1/chat/completions`, bearer authentication, and non-streaming responses. The authenticated `GET /v1/models` listed `gemma-4-26b` during the live check. A real Darkbloom run succeeded on November 7, 2026 after account credits were added: six articles produced three profiles with validated quotes in 3.605 seconds. See docs/darkbloom-live-check.md for execution evidence. It uses only the synthetic portfolio corpus, and does not assert that API compatibility proves private execution or attestation. Ollama defaults to `http://127.0.0.1:11434` and `llama3:8b`.
